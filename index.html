MÓDULO 01 · FASE 1 — LINUX
Mentalidade SRE
O trabalho real não é decorar comandos — é entender sistemas, detectar padrões e investigar causas raiz.
Iniciante
~30 min
📖 Teoria
🧪 Prática
✅ Checklist
🎯 O que realmente importa
Antes de qualquer comando, existe algo mais importante: a mentalidade certa.
O trabalho real de Infra/SRE/DevOps
Não é decorar Kubernetes. Não é memorizar YAML. É entender sistemas, detectar padrões, investigar sintomas, encontrar causa raiz, reduzir impacto e evitar recorrência.
🔥 Método: Hipóteses
Analistas fortes trabalham por hipóteses, não por adivinhação
Hipótese 1
"A lentidão pode ser DNS" → valido com dig e curl
Descarte
DNS descartado (latência normal) → próxima hipótese
Hipótese 2
"Pode ser banco lento" → valido com slow query log
Causa Raiz
Lock no banco por query sem índice → encontrada!
🚨
Erro clássico: Reiniciar o serviço sem investigar primeiro. Restart mascara o sintoma e destrói evidências. SEMPRE colete logs, métricas e estado ANTES de reiniciar.
📋 Frases que carregam experiência operacional
Sintoma não é causa.
CPU alta, timeout, 500 — são sintomas. A causa pode estar em qualquer camada.
Restart apaga evidência.
Capture logs e estado antes de qualquer intervenção.
Hipótese sem validação é chute.
Meça. Prove. Descarte. Avance.
Observabilidade reduz medo.
Quem não sabe observar o sistema trabalha no escuro.
Timeouts geram cascatas.
Sistemas distribuídos amplificam falhas em cadeia.
🧪 Exercício Mental: Os 5 Porquês
Técnica poderosa para chegar à causa raiz real.
Cenário: Sistema caiu
Por quê?
Memória acabou
Por quê?
Vazamento de memória
Por quê?
Cache sem limite configurado
Por quê?
Feature nova implementada sem review
Por quê?
Causa raiz: Processo sem review de arquitetura
✅
Agora chegamos em processo. A solução não é só corrigir o bug — é implementar review de arquitetura para novas features.

MÓDULO 02 · FASE 1 — LINUX
CPU & Processos
CPU alta nem sempre é problema. Aprenda a interpretar load average, iowait, syscalls e identificar gargalos reais.
Intermediário
~45 min
📖 Teoria
⚙️ Comandos
🧪 Laboratório
✅ Checklist
💡
CPU alta NÃO significa necessariamente problema. A pergunta certa é: CPU alta está impactando o tempo de resposta?
📊 Interpretando o comando top
bash
top

# Output típico:
top - 14:32:01 up 5 days, load average: 2.10, 1.85, 1.42
Tasks: 312 total, 2 running, 310 sleeping
%Cpu(s): 45.2 us, 12.1 sy, 0.0 ni, 30.5 id, 8.4 wa, 0.0 hi, 3.8 si
MiB Mem: 16384.0 total, 2048.0 free, 12000.0 used, 2336.0 buff/cache
MiB Swap: 4096.0 total, 3800.0 free, 296.0 used
us — User space
Tempo executando aplicação. Alta = aplicação consumindo CPU. Investigue qual processo.
sy — Kernel/system
Alta = syscalls, IO, networking, kernel pressure. Pode indicar problema de driver ou IO intenso.
wa — I/O wait
CPU esperando disco. MUITO importante! Alta = disco lento, storage ruim, gargalo IO.
id — Idle
CPU ociosa. Se baixo, sistema está sob carga. Se alto mesmo com lentidão, o problema não é CPU.
⚠️ Load Average — o mais incompreendido
⚠️
Load Average NÃO é uso de CPU. É a quantidade de processos na fila (esperando CPU + esperando I/O). Um sistema de 4 cores com load 4.0 está saturado. Com load 2.0 ainda tem folga.
bash
# Ver load e número de cores
uptime
14:32 up 5 days, load average: 2.10, 1.85, 1.42
                              ^1min  ^5min  ^15min

nproc  # número de CPUs/cores
4

# Regra: load / nproc > 1.0 = saturação
# 2.10 / 4 = 0.52 = OK neste caso

MÓDULO 03 · FASE 1 — LINUX
Memória
O erro clássico: "memória usada = problema". Linux usa RAM para cache — isso é bom. Aprenda o que realmente importa.
Intermediário
~40 min
📖 Teoria
⚙️ Comandos
🧪 Laboratório
✅ Checklist
✅
"Memória usada = ruim" é o erro mais comum. Linux usa RAM livre para cache de disco — isso acelera o sistema. Ver "used: 14GB" de 16GB é NORMAL e bom.
🔍 Interpretando free -h
bash
free -h

              total    used    free   shared  buff/cache  available
Mem:          15.6G   10.2G   1.1G    450M       4.3G       4.8G
Swap:          4.0G   280M    3.7G

# "available" é o que importa — não "free"!
# available = free + buff/cache (recuperável)
# 4.8G disponível significa sistema saudável
available — O que importa
Memória real disponível para novos processos. Inclui cache recuperável. Use este número!
swap em uso excessivo
Swap alto significa memória RAM esgotada. O sistema está paginando para disco. Performance destruída.
💀 OOM Killer — o assassino silencioso
OOM = Out Of Memory Killer
Quando a memória acaba, o kernel mata processos para sobreviver. Processo misteriosamente "desaparecendo"? Verifique!
bash
# Verificar se OOM Killer agiu
dmesg | grep -i oom
Out of memory: Kill process 14523 (java) score 847 or sacrifice child
Killed process 14523 (java) total-vm:4194304kB, anon-rss:3221225kB

# Nos logs do sistema
journalctl -k | grep -i "killed process"

# Score de cada processo (quanto maior, mais propenso a ser morto)
cat /proc/14523/oom_score
⚙️ Comandos de Memória
free -h
Visão geral de memória RAM e swap
free -h -s 2
vmstat 1
Estatísticas de memória em tempo real. Observe swpd e wa
vmstat 1 10
/proc/meminfo
Detalhes completos da memória do kernel
cat /proc/meminfo
smem
Uso real de memória por processo (PSS)
smem -r | head
dmesg
Mensagens do kernel — incluindo OOM events
dmesg | grep -i oom
pmap
Mapa de memória de um processo específico
pmap -x PID
⚠️
Swap ≠ RAM. Swap é uma válvula de emergência no disco. Se você está usando swap constantemente, o sistema precisa de mais RAM. Swap alto = performance destruída.
🧪 Lab 03 — Investigar uso de memóriaLAB
FÁCIL
1

2

3
Verifique se houve eventos OOM: dmesg | grep -i oom | tail -5
4

5

✅ Checklist — Memória
Sei interpretar free -h corretamente (available, não free)
Entendo que buff/cache é memória utilizável, não desperdiçada

MÓDULO 04 · FASE 1 — LINUX
Disco & I/O
Disco lento destrói sistemas silenciosamente. Aprenda a identificar gargalos de I/O antes que eles destruam a produção.
📖 Teoria
⚙️ Comandos
✅ Checklist
🚨
Disco lento é o problema invisível. CPU pode estar baixa, memória pode estar OK, mas se o disco está saturado, o sistema inteiro degrada silenciosamente.
📊 iostat — a ferramenta chave
bash
iostat -xz 1

Device:  rrqm/s wrqm/s  r/s  w/s  rkB/s  wkB/s  avgrq-sz avgqu-sz  await  r_await w_await svctm  %util
sda        0.0    0.0  0.0  98.0    0.0  392.0      8.0     2.4    24.3     0.0    24.3   8.2   80.3

# INTERPRETAÇÃO:
# %util = 80.3% → disco muito ocupado (acima de 80% = problema)
# await = 24.3ms → latência de 24ms (alto! SSD deve ser < 1ms)
# avgqu-sz = 2.4 → fila de 2.4 operações esperando
%util perto de 100%
Disco saturado. Cada nova operação de I/O vai esperar na fila. Sistema em colapso.
await alto
Latência de acesso ao disco. SSD normal: <1ms. HDD normal: 5-10ms. Acima disso: problema de hardware ou saturação.
bash
# Verificar espaço em disco
df -h
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   48G  2.0G  97% /         ← CRÍTICO!

# Encontrar o que está ocupando espaço
du -sh /var/log/* | sort -rh | head -10

# Encontrar arquivos grandes
find / -size +1G -type f 2>/dev/null
⚙️ Comandos de Disco
df -h
Espaço livre/usado em todos os filesystems
df -h /var
iostat -xz 1
Estatísticas de I/O por dispositivo em tempo real
iostat -xz 1 5
du -sh
Tamanho de diretórios/arquivos
du -sh /var/log/*
lsof
Quais processos estão usando quais arquivos
lsof /var/log/app.log
iotop
Processos com mais I/O (como top para disco)
iotop -ao
hdparm -t
Teste de velocidade de leitura do disco
hdparm -t /dev/sda
✅ Checklist — Disco & I/O
Sei interpretar %util e await no iostat
Consigo encontrar o que está lotando o disco com du/find
Entendo a diferença entre await de SSD vs HDD
MÓDULO 05 · FASE 2 — REDE
TCP/IP & DNS
Grande parte dos problemas de produção não são bugs — são problemas de rede. DNS resolve 40% dos incidentes "misteriosos".
Fundamental
~60 min
📖 Teoria
🔌 TCP na Prática
🌐 DNS
✅ Checklist
🌐 O modelo mental da rede
Toda comunicação tem: origem → protocolo → porta → destino → latência → handshake → timeout. Quando algo falha, um desses elementos é o culpado.
📡 Estados TCP que você deve conhecer
EstadoSignificadoNormal?Quando preocupar
ESTABLISHEDConexão ativaNORMALMuitas demais pode indicar leak
TIME_WAITAguardando encerramento seguroNORMALCentenas de milhares = problema
CLOSE_WAITRemoto fechou, local nãoATENÇÃOAumentando = bug de código (não fecha conexão)
SYN_SENTEsperando resposta do handshakeNORMALAcumulando = timeout/firewall bloqueando
LISTENPorta escutando conexõesNORMALPorta que deveria escutar não está
bash
# Ver todas as conexões com processo
ss -tunap

# Contar conexões por estado
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn

# Quem está escutando em qual porta
ss -tlnp
State   Recv-Q  Send-Q  Local Address:Port    Peer Address:Port
LISTEN  0       128     0.0.0.0:80             0.0.0.0:*    users:(("nginx",pid=1234,fd=6))
LISTEN  0       128     0.0.0.0:443            0.0.0.0:*    users:(("nginx",pid=1234,fd=7))
🔌 TCP — Handshake & Timeout
O handshake TCP (3-way)
Cliente → Servidor
SYN — "Quero conectar"
Servidor → Cliente
SYN-ACK — "OK, pode conectar"
Cliente → Servidor
ACK — "Confirmado, conectado!"
⚠️
Timeout é um sintoma, não uma causa. Quando vê "connection timed out", investigue: firewall? Rota de rede? Serviço caído? DNS incorreto? Congestionamento?
bash
# Capturar tráfego TCP para debug
tcpdump -i eth0 -n port 443 -w capture.pcap

# Ver handshake em tempo real
tcpdump -i eth0 "tcp[tcpflags] & (tcp-syn) != 0"

# Ver retransmissões (problema de rede)
tcpdump -i eth0 "tcp[tcpflags] & (tcp-rst) != 0"

# Testar conectividade TCP básica
nc -zv api.exemplo.com 443
Connection to api.exemplo.com 443 port [tcp/https] succeeded!
🌐 DNS — O causador oculto
🚨
Muitos sistemas "caindo" são apenas DNS. Resolução lenta, cache errado, DNS intermitente, propagação incompleta — todos causam falhas que parecem bug de aplicação.
bash
# Resolver DNS básico
dig google.com
dig +short api.exemplo.com

# Medir tempo de resolução DNS
dig google.com | grep "Query time"
;; Query time: 2 msec   ← bom
;; Query time: 3000 msec ← problema de DNS!

# Forçar DNS resolver específico
dig @8.8.8.8 api.exemplo.com

# Verificar configuração DNS local
cat /etc/resolv.conf

# Reverso — IP para hostname
dig -x 8.8.8.8

# Simular propagação — verificar múltiplos resolvers
dig @1.1.1.1 api.exemplo.com  # Cloudflare
dig @8.8.8.8 api.exemplo.com  # Google
🐛 Problemas clássicos de DNS
ProblemaSintomaDiagnóstico
Resolução lentaTudo lento, mesmo com servidor funcionandodig +stats domain.com — observe Query time
Cache erradoDNS retorna IP antigo após trocadig @8.8.8.8 vs dig @1.1.1.1
DNS intermitenteÀs vezes funciona, às vezes nãofor i in $(seq 10); do dig +short domain.com; done
NXDOMAINDomínio não existe / digitado erradoVerificar configuração e spelling
TTL alto após mudançaMudança não propagoudig domain.com | grep TTL

MÓDULO 06 · FASE 2 — REDE
Ferramentas de Rede
curl, dig, ss, tcpdump — o arsenal completo para investigar qualquer problema de rede em produção.
🔧 curl
🦈 tcpdump
✅ Checklist
🔧 curl — ferramenta obrigatória
💡
Aprenda MUITO curl. É sua navalha suíça para testar APIs, certificados, latência, headers e muito mais.
bash
# Verbose — ver tudo (headers, TLS, timing)
curl -v https://api.site.com

# Medir timing detalhado
curl -o /dev/null -s -w "\nDNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nTTFB: %{time_starttransfer}s\nTotal: %{time_total}s\n" https://api.site.com

# Seguir redirects
curl -L https://site.com

# POST com JSON
curl -X POST -H "Content-Type: application/json" -d '{"key":"value"}' https://api.site.com

# Ignorar SSL (só para debug!)
curl -k https://api-interno.com

# Testar com header de host específico
curl -H "Host: api.site.com" http://10.0.0.5/health

# Verificar certificado
curl -v -o /dev/null https://site.com 2>&1 | grep -E "expire|SSL|TLS"
🦈 tcpdump — o superpoder
⚡
Pouca gente domina tcpdump. Quem domina resolve problemas absurdos. É a ferramenta definitiva para ver exatamente o que está passando na rede.
bash
# Capturar tráfego na porta 443
tcpdump -i eth0 port 443

# Salvar captura para análise no Wireshark
tcpdump -i eth0 -w capture.pcap port 443

# Ver tráfego de/para IP específico
tcpdump -i eth0 host 10.0.0.5

# Ver resets TCP (conexões forçadamente encerradas)
tcpdump -i eth0 "tcp[tcpflags] & tcp-rst != 0"

# Capturar DNS
tcpdump -i eth0 port 53 -n

# Ver conteúdo em ASCII
tcpdump -i eth0 -A port 80
📋 O que procurar no tcpdump
RST repetidos
Conexões sendo brutalmente encerradas. Indica firewall, serviço caído ou rejeição ativa.
Retransmissões
Pacotes perdidos sendo reenvidos. Indica problema de rede ou congestionamento.
SYN sem resposta
Pacote de handshake vai mas não volta. Firewall bloqueando ou serviço não está rodando.
Handshake limpo
SYN → SYN-ACK → ACK em sequência rápida. Conexão TCP saudável.
✅ Checklist — Ferramentas de Rede
Sei usar curl -v e interpretar o output completo
Consigo medir DNS/connect/TLS/TTFB com curl -w
Sei capturar tráfego com tcpdump e filtrar por porta/IP
Consigo identificar RST, retransmissões e SYN sem resposta
MÓDULO 07 · FASE 3 — OBSERVABILIDADE
Logs
Logs são evidência. Mas muita gente lê errado — linha por linha, sem padrão. Aprenda a extrair inteligência de logs.
📖 Como Ler
🔍 grep & filtros
🧪 Laboratório
✅ Checklist
📖 Como ler logs corretamente
⚠️
NÃO leia linha por linha primeiro. Você vai se perder. Primeiro identifique padrões, depois filtre, depois correlacione.
1. Identificar padrão
Mesmo erro? Com que frequência? Em que horário? Qual componente?
2. Filtrar
grep para isolar o que importa. Eliminar ruído.
3. Correlacionar
Deploy? Horário de pico? Aumento de tráfego? Mudança recente?
📋 journalctl — logs do systemd
bash
# Logs de um serviço específico
journalctl -u nginx

# Últimas 100 linhas em tempo real
journalctl -u nginx -n 100 -f

# Logs com erros (priority = error)
journalctl -p err

# Logs desde um horário
journalctl --since "2024-01-15 10:00:00" --until "2024-01-15 11:00:00"

# Logs do kernel
journalctl -k

# Output JSON para processar
journalctl -u nginx -o json
🔍 grep — uma arma de investigação
bash
# Básico — buscar erro
grep -i "error" app.log

# Múltiplos padrões com regex
grep -E "500|timeout|exception" app.log

# Contexto — 5 linhas antes e depois do erro
grep -C 5 "ERROR" app.log

# Contar ocorrências
grep -c "ERROR" app.log

# Com timestamp — frequência de erros
grep "ERROR" app.log | awk '{print $1}' | sort | uniq -c | sort -rn

# Excluir padrões (inverso)
grep -v "health-check" access.log | grep "500"

# Em múltiplos arquivos
grep -r "OutOfMemoryError" /var/log/

# Contar erros 500 por minuto (análise de padrão)
grep " 500 " access.log | cut -d' ' -f4 | cut -c1-17 | sort | uniq -c
⚙️ tail & watch — logs em tempo real
bash
# Acompanhar log em tempo real
tail -f /var/log/app.log

# Acompanhar E filtrar em tempo real
tail -f /var/log/app.log | grep --line-buffered "ERROR"

# Múltiplos arquivos ao mesmo tempo
tail -f /var/log/app.log /var/log/nginx/error.log

Métricas & Alertas
Golden Signals, RED Method, USE Method. Aprenda o que medir e como alertar sem criar fadiga operacional.
📖 Métodos
🔔 Alertas
✅ Checklist
📊 Os 3 métodos essenciais
⭐ Golden Signals
Latência — tempo de resposta
Tráfego — req/segundo
Erros — taxa de falha
Saturação — limite de recurso
🔴 RED Method
Rate — quantas requests
Errors — quantos erros
Duration — tempo de resposta
Ideal para microsserviços
🔧 USE Method
Utilization — % usando
Saturation — existe fila?
Errors — existe falha?
Ideal para infraestrutura
📈 Diferença entre Logs, Métricas e Traces
PilarMostraIdeal paraExemplo
LogsEvento detalhado individualDebug de erros específicosStack trace de uma exception
MétricasComportamento agregado no tempoTendências, alertas, dashboardsLatência p99 dos últimos 5 min
TracesJornada de uma requisiçãoPerformance de sistemas distribuídosRequest passou por API → DB → Cache
🔔 Alertas que funcionam
🚨
O maior erro: alertar tudo. Isso cria fadiga de alerta — a equipe para de tomar alertas a sério. Quando o alerta real chega, é ignorado.
❌ Alerta ruim
"CPU acima de 80%"
"Mais de 10 erros por minuto"
"Disco com menos de 20% livre"
Não é acionável. Pode ser normal. Sem contexto.
✅ Alerta bom
"Taxa de erro /api/checkout > 1% por 5min"
"Latência p99 > 2s por 10min"
"Disco enche em < 4h no ritmo atual"
Acionável, específico, com contexto temporal.
Características de um bom alerta
✅ Acionável — tem uma ação clara quando dispara
✅ Específico — indica qual serviço, qual métrica, qual threshold
✅ Relevante — impacta o usuário ou está prestes a impactar
✅ Contextualizado — tem janela temporal (não dispara em spike de 1s)
✅ Urgente de verdade — precisa de atenção humana agora
✅ Checklist — Métricas & Alertas
Sei aplicar Golden Signals para qualquer serviço
Entendo a diferença entre RED Method (serviços) e USE Method (infra)
Sei distinguir logs, métricas e traces e quando usar cada um
Consigo avaliar se um alerta é acionável e específico
MÓDULO 09 · FASE 4 — TROUBLESHOOTING
Método Universal de Troubleshooting
O fluxo mental que separa quem investiga de quem chuta. Aprenda a metodologia que profissionais sênior usam.
Avançado
~60 min
📋 Método
🧠 Mapa Mental
🔥 Cenário Real
✅ Checklist
💡
Regra número 1: NUNCA comece tentando resolver. Primeiro entenda, observe, colete evidências.
📋 Os 5 Passos Universais
1
Qual é o sintoma?
Lentidão? Erro 500? Timeout? CPU alta? Pod reiniciando? Sintoma ≠ causa raiz. Documente exatamente o que está acontecendo.
2
O problema é local, sistêmico, intermitente ou contínuo?
Um usuário? Todos? Às vezes? Sempre? Isso muda completamente a investigação. Problema intermitente sugere condição de corrida, load balancer ou DNS.
3
O que mudou?
Esta pergunta resolve MUITOS incidentes. Deploy? DNS? Certificado? Firewall? Feature flag? Banco? Configuração? A maioria dos incidentes tem uma mudança como gatilho.
4
É reproduzível?
Se consegue reproduzir, consegue medir, testar e validar. Um bug reproduzível é meio caminho andado para a solução.
5
Isole as camadas
App lenta → CPU? Memória? Disco? DNS? Banco? API externa? GC? Elimine hipóteses sistematicamente. Não resolva antes de identificar a camada.
🧠 Checklist mental rápido por camada
🖥️ CPU
□ top → load average
□ us alto → qual processo?
□ wa alto → disco?
□ sy alto → kernel pressure?
💾 Memória
□ free -h → available
□ swap em uso?
□ dmesg → OOM?
□ ps → maior consumidor
💿 Disco
□ df -h → espaço livre
□ iostat → %util, await
□ iotop → quem faz I/O
□ du → o que ocupa espaço
🌐 Rede
□ dig → DNS resolvendo?
□ ping → latência básica
□ ss → conexões CLOSE_WAIT
□ tcpdump → tráfego real
📱 Aplicação
□ logs → exceções, padrões
□ pool de conexões cheio?
□ GC pausando?
□ thread dump / goroutines
🗄️ Banco
□ slow query log
□ locks ativos
□ conexões simultâneas
□ CPU/IO do servidor DB

🚨
Incidente em produção às 14h32: Usuários reportando lentidão extrema no checkout. Erros 500 esporádicos. Ops team acordado.
📅 Timeline do incidente

14:28
CPU começa a subir no serviço de pagamento
14:30
Latência do /api/payment sobe de 80ms para 2400ms
14:32
Alertas de erro 500 disparam. Equipe acionada.
14:33
Serviço de carrinho começa a falhar (dependia do payment)
14:34

14:36

14:42

14:45
Sistema normaliza gradualmente
🔍 Investigação passo a passo
Como deveria ter sido investigadoANÁLISE
1
Sintoma: Lentidão no checkout. Erros 500. Não reiniciar nada ainda.
2
Pergunta-chave: "O que mudou?" → Deploy às 14:25. Correlação temporal clara.
3
Isolar: grep "ERROR" payment.log | tail -50 — confirmar que é só /api/payment
4
CPU: top → us alto no processo payment-service → app consumindo CPU
5
Decisão rápida: Rollback do deploy (mudança recente + CPU alta = causa clara)
6
Validar: Monitorar métricas após rollback. CPU baixa → sistema normaliza → causa confirmada.
✅
Lição: Deploy recente + problema imediato = rollback primeiro, investigação depois. A pergunta "o que mudou?" economizou horas de debug.

MÓDULO 10 · FASE 4 — TROUBLESHOOTING
Incidentes & Postmortem
Postmortem não é sobre encontrar culpado — é sobre entender o sistema e evitar recorrência.
📖 Postmortem
📝 Template
✅ Checklist
📋 O que é um postmortem real
❌ O que NÃO é
— Encontrar culpado
— Punir alguém
— Lista de blame
— Reunião de cobranças
✅ O que É
— Entender o sistema
— Reduzir recorrência
— Melhorar processo
— Aprendizado coletivo
💡
Cultura blameless: Se alguém com as mesmas informações disponíveis tomaria a mesma decisão, o problema é sistêmico — não da pessoa. O sistema permitiu o erro.
📝 Template de Postmortem
1. Resumo
O que aconteceu em 2-3 frases. Impacto resumido. Para quem, quando, por quanto tempo.
2. Impacto
Quantos usuários afetados? Qual % do tráfego? Qual serviço? Quanto tempo de indisponibilidade?
3. Timeline
Linha do tempo cronológica. Cada evento com horário. Inclui quando foi detectado, quando acionou, quando foi resolvido.
4. Root Cause
A causa raiz real — não o sintoma. Use os 5 Porquês para chegar ao fundo.
5. Contributing Factors
O que piorou o incidente? Falta de alerta? Processo de deploy? Falta de circuit breaker?
6. Detection & Resolution
Como detectamos? Quanto tempo levou? Como resolvemos? Poderia ter sido mais rápido?
7. Action Items
Ações concretas com owner e prazo. Cada action item deve ser: mensurável, com responsável, com data.
✅ Checklist — Incidentes & Postmortem
Sei coletar evidências ANTES de intervir
Consigo montar timeline com horários precisos
Entendo a diferença entre causa raiz e sintoma
Sei escrever action items acionáveis com owner e prazo
MÓDULO 11 · FASE 5 — KUBERNETES
Kubernetes na Prática
Kubernetes não é magia. É Linux + Rede + Processos + Scheduling distribuídos. Os fundamentos continuam os mesmos.
📖 Conceitos
🔧 Debug
✅ Checklist
💡
Kubernetes é Linux distribuído. Pod = processo isolado. Service = rede. DNS = descoberta de serviço. Limits = cgroups. Probes = healthcheck.
🧩 Conceitos essenciais
Pod
Menor unidade. Um ou mais containers compartilhando rede e storage. Como um processo no Linux.
Service
Abstração de rede. IP estável que roteia para pods. ClusterIP, NodePort, LoadBalancer.
Deployment
Gerencia ReplicaSets. Controla rollout, rollback e escala de pods.
Ingress
Roteamento HTTP/HTTPS externo. Regras de path e host para serviços internos.
Requests/Limits
CPU e memória garantidos (request) vs máximo (limit). Sem limits → pod pode derrubar o node.
Probes
Liveness = "ainda vivo?". Readiness = "pronto para receber tráfego?". Startup = "inicializando".
🚨
Erro clássico: "Pod restartando = problema resolvido". Não. Você apenas apagou evidência. O pod restartou porque o liveness probe falhou. Por quê falhou? Essa é a pergunta.
🔧 Debug de Pods
bash
# Status de todos os pods
kubectl get pods -A

# Detalhes de um pod específico
kubectl describe pod meu-pod

# Logs em tempo real
kubectl logs -f meu-pod

# Logs do container anterior (se reiniciou)
kubectl logs meu-pod --previous

# Shell dentro do pod
kubectl exec -it meu-pod -- /bin/sh

# Eventos do namespace (o que aconteceu)
kubectl get events --sort-by=.lastTimestamp

# Verificar uso de recursos
kubectl top pods
kubectl top nodes
